# 記入例：クラッシュ率の改善とリリース手順の整備

以下は、記録方法を示す仮の例です。特定のチームの実績を示すものではありません。

| 項目 | 記入例 |
| :--- | :--- |
| 関連チェック項目 | No.050：公開後の段階的公開の間にクラッシュ率などの変化を検知し、公開停止・無効化・修正版の申請を判断できること。 |
| 対象範囲 | 対象アプリのiOS・Android両方のストア公開と、公開後7日間の監視。 |
| 個人のスキル | 担当者の`mobile.observability`は、別途確認した設定・分析の証拠によりLv2。`mobile.release`はLv1。 |
| チームの現状 | クラッシュ収集サービスは導入済みだが、バージョン別のクラッシュ率を公開判断に使う基準がなく、段階的公開の停止を判断した実績もない。 |
| 原文への回答・判定 | FALSE・未達。 |
| 原因・制約 | 公開の判断者、監視期間、許容するクラッシュ率の基準が未定義であり、ストアアカウントの公開操作権限が一人に集中している。 |
| 行うこと | 監視期間、許容基準、判断者を決める。段階的公開の停止、機能フラグによる無効化、修正版の緊急申請の手順を文書化し、演習する。公開操作の権限を複数人に付与する。 |
| 担当と支援 | 開発担当者が基準と手順を作成し、テックリードが判断基準の妥当性、運用担当者が権限付与とアカウント管理を支援する。 |
| 完了条件 | 直近2回の公開で、基準に沿って監視と判断を記録している。別のメンバーが手順を使って段階的公開を停止できる。 |
| 効果の確認 | 導入後3か月の公開について、公開から異常検知までの時間、停止・修正の判断記録、修正版が利用者に到達するまでの日数を確認する。 |

この例では、まず判断基準と運用手順を整備する必要があります。担当者が一度手順を作成したことだけでLv4とは判定しません。個人の習熟度は、[スキル定義](../skills/index.md)の該当定義と本人の行動に照らして別に確認します。
