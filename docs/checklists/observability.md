# モニタリングとクラッシュ分析

**項目No.：073〜076**

回答例は望ましい状態を示す架空の文面です。[判定方法](../guide/team-assessment.md)と[記録書式](../templates/team-assessment.md)を使い、実態と根拠を記録してください。

## この分野の背景

この分野は、アプリとサーバーの状態を常に見守り、クラッシュ（アプリの異常終了）やエラーの情報を集めて原因を調べ、改善につなげる取り組みです。モバイルアプリは利用者ごとに異なる端末と通信環境で動くため、開発者の手元では再現しない問題が多く、端末から情報を集める仕組みがなければ問題に気付くこともできません。原文の「フロントエンド」はモバイルアプリに読み替えます。まず、クラッシュの件数をアプリのバージョン別に確認できる画面があるかを確かめてください。

分からない用語は[用語集](../guide/glossary.md)で確認できます。

## C073

**チェック項目 No.073**

SLI/SLOに関わるシステムの稼働を24時間365日モニタリングしている。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

アプリが依存するAPIとプッシュ通知（サーバーから端末へ送る通知）の送信基盤についてSLI（サービスの品質を測る指標）を定義し、可用性、応答時間、エラー率を24時間365日、自動で監視しています。アプリ側でもクラッシュが発生しなかった利用者の割合と主要操作の成功率をSLIに含め、アプリとOSのバージョン別に確認しています。SLO（SLIについて定めた目標値）の評価期間・目標値・対象範囲を明記し、目標からの逸脱や急激な悪化に加えて監視の停止も検知できます。

[原文の参照先](https://dxcriteria.cto-a.org/197aa2a71774476a80eaeef043dadb1b)

## C074

**チェック項目 No.074**

エラーログを収集し、定期的（月ごと〜半年ごと）にエラーの傾向を分析し、その結果をもとに改善活動を計画している。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

Firebase Crashlytics（クラッシュ収集・分析サービス）などでクラッシュ、ANR（Androidでアプリが応答しなくなった状態）、捕捉したエラーを収集し、サーバーのエラーログと併せて月次で傾向を分析しています。発生件数、影響する利用者数、アプリとOSのバージョン、端末、リリースとの関係を確認し、影響と頻度から改善対象を選んで担当者・期限・完了条件を設定しています。原因箇所を特定できるよう、ビルドごとにシンボル情報（クラッシュ位置をソースに対応付けるための、iOSのdSYMファイルとAndroidのR8マッピングファイル）をアップロードしています。対策を含むバージョンが普及した後に発生傾向を比較し、再発の有無を確認しています。

[原文の参照先](https://dxcriteria.cto-a.org/a96a63a4179c4a319c39301411d1274c)

## C075

**チェック項目 No.075**

各種事象を調査する際にバックエンド、インフラ、フロントエンドに渡って統合されたログをトレースできるようになっている。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

アプリの画面操作からAPI、バックエンド処理、インフラの記録まで、アプリが付与するリクエストID（送信ごとに付ける一意の識別子） やトレースID（一連の処理をつなぐための識別子） で関連付けて調査できます。アプリのログにはアプリのバージョン、OSバージョン、端末の機種、通信状態を含め、時刻の形式をサーバー側と統一しています。個人情報や認証情報は送信前に除外し、代表的な障害を使って追跡できることを確認しています。

[原文の参照先](https://dxcriteria.cto-a.org/9dd3fd228f6240d184ef6679c88a2b88)

## C076

**チェック項目 No.076**

モニタリングにおける異常検知時のアラートが設定されていなかったり、対応フローが確立しておらず問題が解決されなかったりしている。

**望ましい原文への回答：FALSE**

原文にある問題が発生していない状態を目指します。

### 望ましい回答例

クラッシュ率（アプリが異常終了したセッションの割合）の急増、特定バージョンでの新しいクラッシュ、APIのエラー率、プッシュ通知の送信失敗について、検知条件、重大度、通知先、一次対応、エスカレーション（上位の担当者や他チームへの引き継ぎ）、復旧確認までの手順を定めています。通知に応答がない場合の連絡経路も用意しています。定期的な訓練で通知から段階的公開（一部の利用者から順に新版を配布する仕組み）の停止判断までを確認し、担当不明や通知未設定によって問題が放置される状態を防いでいます。

[原文の参照先](https://dxcriteria.cto-a.org/4e236d711c09478392092ad957948336)
