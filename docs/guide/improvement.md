# 評価結果を改善につなげる

## 原因に合わせて対応を選ぶ

個人の習熟度とチームの判定を並べ、何を変えれば担当業務を完了できるかを考えます。目標Lvとの差だけで原因を決めず、作業時間、権限、環境、業務分担も確認します。

| 確認した状態 | 対応の方向 | 完了を確認する例 |
| :--- | :--- | :--- |
| 本人が標準的な作業を完了するために支援を必要とする。 | 演習、ペア作業、段階的な実務担当で習得を支援します。 | 別の同等課題で、本人が実装・検証・修正を完了できる。 |
| 実行できる人はいるが、チーム共通の環境や手順がない。 | 共通設定、CI、手順書、権限、支援窓口を整備します。 | 別のメンバーが同じ手順で実行し、結果を確認できる。 |
| 環境はあるが、使い方や担当が共有されていない。 | 導入時の説明、担当の明確化、実行機会の確保を行います。 | 対象メンバーが利用し、必要時に問題を切り分けられる。 |
| 特定の人だけが対応できる。 | 共同作業と担当交代を行い、代替担当者を育成します。 | 主担当者が不在でも、別の担当者が対象作業を完了できる。 |
| 技術的には実行できるが、対応が計画に入らない。 | 優先順位、保守工数、責任分界を見直します。 | 改善作業が計画され、期限内に実施される。 |
| 証拠がなく、状態を判断できない。 | 追加調査や演習を行います。 | 確認結果に基づいて判定を付けられる。 |

モバイルアプリでは、署名鍵、ストアアカウント、検証用端末、CI用のmacOS実行環境など、特定の担当者や環境に依存しやすい要素があります。「特定の人だけが対応できる」状態は、担当者の異動やOSの更新時に公開の停滞として現れるため、早めに代替担当者と手順を整備します。

## チェック項目とスキルの結び付け方

次の表は、改善を検討する際の関連付けの例です。チェック項目の達成を、記載したスキルのLvへ直接換算するものではありません。

| チェック項目の例 | 関連するスキルの例 | 併せて確認する条件 |
| :--- | :--- | :--- |
| No.002〜003：型検査、APIの型連携 | `swift.basic`、`kotlin.basic`、`mobile.api-integration` | API仕様の管理者、CI設定、バックエンドとの合意 |
| No.009〜012：UI部品の共通化と設計 | `swiftui.basic`、`compose.basic`、`react-native.basic`、`mobile.ui-design` | カタログの更新担当、デザインとの合意、変更・廃止の手順 |
| No.021〜024：性能の計測と改善 | `mobile.performance`、`swift.concurrency`、`kotlin.coroutines` | 計測環境、監視担当、性能目標、対象端末 |
| No.025〜028：アクセシビリティ | `mobile.accessibility`、`mobile.ui-design` | 品質基準、デザインとの合意、支援技術を使った確認機会 |
| No.029〜036：セキュリティ、権限とプライバシー | `mobile.security`、`mobile.persistence`、`mobile.release` | 検査基盤、修正期限、法務・専門担当者への相談経路 |
| No.041〜044：テストの計画と保守 | `test.design`、`test.unit`、`test.ui` | 仕様の確定、検証用端末、テストデータ、保守時間 |
| No.049〜052：署名・配布・ストア審査 | `mobile.release`、`mobile.cicd`、`mobile.observability` | 署名鍵・ストアアカウントの権限、審査期間、段階的公開の判断者 |
| No.057〜060：CI/CDの運用 | `git.collaboration`、`mobile.cicd`、`build.tooling` | CI実行環境（macOSランナー等）、権限、共有基盤との責任分界 |
| No.065〜072：端末・OS互換性、オフラインと同期 | `mobile.basic`、`mobile.persistence`、`mobile.api-integration` | サポート方針、利用者の端末分布、検証用端末、バックエンドとの合意 |
| No.089〜092：職能・役割・育成 | 担当業務に必要な各スキル | 担当機会、支援者、学習時間、代替要員 |

## 改善の優先順位

優先順位は、業務への影響と対応の緊急性から決めます。利用者の操作を止めるクラッシュ、機密情報の露出、ストア審査の差し戻しによる公開停止、OS更新による動作不良などは、定例の評価を待たずに対応します。

通常の改善では、影響する利用者・チームの範囲、発生頻度、手戻りや待ち時間、必要工数、他の施策への依存関係を比較します。ストアで配布したアプリは旧バージョンが利用者の端末に残り続けるため、修正の到達に時間がかかる問題を優先します。全項目の達成を一度に目指すのではなく、次の期間に完了できる改善を選びます。

## 役割と見直しの頻度

| 役割 | 責任 |
| :--- | :--- |
| 本人 | 実績と支援を受けた範囲を説明し、次の課題に取り組みます。 |
| スキル評価者 | [スキル定義](../skills/index.md)と証拠を照合し、判定の根拠と次の到達条件を明確にします。 |
| チームの確認責任者 | チェックリストの適用範囲、証拠、判定を取りまとめます。 |
| 改善責任者 | 改善の優先順位、担当者、工数、期限を決め、完了と効果を確認します。 |
| 本書の管理者 | 定義と運用方法を管理し、変更履歴を残します。 |

少人数のチームでは、一人が複数の役割を兼ねられます。ただし、自己評価と確認後の判定は分けて記録します。

初期運用では、次の頻度を目安にします。適用時に対象チームの計画へ組み込み、採用した頻度を明記してください。

| 時期・頻度 | 実施内容 |
| :--- | :--- |
| 導入時、案件開始時、担当変更時 | 対象範囲、必要スキル、目標Lv、担当・支援体制を設定します。 |
| 週次 | 着手中の改善と育成課題の進捗、障害、必要な支援を確認します。 |
| 月次 | 完了した施策の効果を確認し、次に取り組む改善と工数を決めます。 |
| OSのメジャーアップデート前 | サポート方針、互換性の確認計画、必要なスキルの不足を確認します。 |
