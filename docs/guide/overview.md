# ガイドの目的と評価の全体像

モバイルアプリ開発の品質と生産性を高めるには、担当者が何を実行できるかに加え、その能力を発揮できる開発環境と運用が必要です。本書では、個人のスキル習熟度とチームの取り組みを共通の基準で確認し、育成・担当配置・開発環境の整備・業務改善につなげます。

本書を使うと、次の三つを整理できます。

1. 担当業務に必要なスキルと、現在実行できる範囲。
2. チームとして実施できている取り組みと、不足している仕組み。
3. 次に取り組む改善、その担当者、完了条件、効果を確認する方法。

個人の評価には、34スキルそれぞれのLv0〜Lv4を使用します。チームの確認には、100項目のチェックリストを使用します。両者は関連しますが、評価対象と判定方法が異なるため、単一の点数へ換算しません。

## 対象読者

| 読者 | 本書を使って行うこと |
| :--- | :--- |
| 開発メンバー | 自分の実行可能な範囲と根拠を整理し、次に習得する内容を決めます。 |
| テックリード・レビュー担当者 | 共通の基準でスキルを確認し、設計・実装・検証の支援範囲を決めます。 |
| プロジェクト責任者・チームリーダー | 必要なスキルを持つ担当者と代替要員を確保し、環境・運用の改善を計画します。 |
| 横断支援・育成担当者 | 複数チームに共通する課題を把握し、標準、共通部品、教材、支援体制を整備します。 |

## モバイルアプリ開発の特徴

モバイルアプリは利用者の端末で動き、ストアの審査を経て配布されます。本書の基準は、次の特徴を前提に作られています。詳しくは[モバイルアプリ開発の前提](mobile-basics.md)を参照してください。

| 特徴 | 評価・改善で意識すること |
| :--- | :--- |
| 修正がすぐに届かない | 審査と利用者の更新を待つため、公開前の検証、段階的公開、機能フラグ、旧バージョンとの互換性を重視します。 |
| 端末とOSが多様 | サポート範囲を決め、代表的な端末とOSで確認します。OSのメジャーアップデート前の対応計画が必要です。 |
| 通信と電源が不安定 | オフライン時の振る舞い、再送、電池消費を設計と検証の対象にします。 |
| OSが権限とライフサイクルを管理 | 権限の要求と拒否時の動作、背面での中断と復帰を実装・確認します。 |
| アプリは解析され得る | 秘密情報をアプリに埋め込まず、端末内の保護領域と通信の保護を使います。 |
| クラッシュは端末で起きる | 収集サービスとシンボル化で把握し、バージョン別に分析します。 |

## 対象とするプラットフォーム

本書はiOS、Android、React Nativeのアプリ開発を対象とします。各スキルには対象プラットフォームを付け、次のように使い分けます。

| 対象 | 意味 | 例 |
| :--- | :--- | :--- |
| 共通 | プラットフォームに依存しない到達状態を定義し、技術名は各ページの「技術の対応」に示す。 | ネットワーク通信、データ永続化、アプリアーキテクチャ、テスト設計 |
| iOS | Apple製プラットフォーム固有の言語・フレームワーク。 | Swift、Swift並行処理、SwiftUI、UIKit |
| Android | Android固有の言語・フレームワーク。 | Kotlin、Kotlinコルーチン・Flow、Jetpack Compose、Android Views・Fragment |
| React Native | JavaScript／TypeScriptでネイティブアプリを構築する方式。 | React Native実装、React Nativeのネイティブ連携 |

担当者は担当するプラットフォームのスキルと、共通スキルを組み合わせて評価します。iOSとAndroidの両方を担当する場合でも、各スキルの習熟度は別々に記録します。React Nativeの前提となるJavaScript、TypeScript、Reactは本書の対象外であり、別の基準で確認します。FlutterやKotlin Multiplatformは本版の対象に含めていません。

## 三つの概念を区別する

| 概念 | 何を表すか | 表記 | 例 |
| :--- | :--- | :--- | :--- |
| スキル領域 | 扱う技術や作業のまとまり | 4つの領域名 | SwiftUIは「フレームワーク・実装領域」に分類します。 |
| スキル習熟度 | 個人が、そのスキルでどこまで実行できるか | Lv0〜Lv4、未評価 | SwiftUIの画面を支援の下で実装できる場合は、基準と証拠を確認してLv1と判定します。 |
| チームの取り組み | 対象チーム・環境で、必要な仕組みが運用されているか | 達成・一部達成・未達・未評価・対象外 | 段階的公開の間にクラッシュ率の変化を検知し、公開停止を判断できる運用があるかを確認します。 |

スキル領域は扱う技術や作業の分類を示し、習熟度のLv0〜Lv4は、そのスキルで実行できる範囲を示します。同じ領域に含まれるスキルでも、個人の習熟度はそれぞれ異なります。例えば、GitはLv3、Kotlinコルーチン・FlowはLv2という状態があります。

## スキル領域

| スキル領域 | 内容 | スキル数 |
| :--- | :--- | :---: |
| 基礎領域 | モバイルプラットフォーム、Swift、Kotlin、開発環境、ビルドと依存管理、Gitの基礎 | 6 |
| 応用基礎領域 | 並行処理、リアクティブ、ネットワーク、永続化、アクセシビリティ、UIデザイン、チーム開発 | 8 |
| フレームワーク・実装領域 | SwiftUI、UIKit、Jetpack Compose、Android Views、React Native、アーキテクチャ、画面遷移、API連携、入力検証、プラットフォーム機能、アニメーション | 12 |
| 品質・高度化領域 | テスト設計・実装、性能、セキュリティ、配布・ストア公開、CI/CD、監視・クラッシュ分析 | 8 |

各領域のスキルは、担当業務と前提知識に応じて組み合わせて学習します。必要な基礎を確認しながらUIフレームワークの実装へ進み、テスト設計やセキュリティも並行して学習できます。

## 個人の能力とチームの条件を分けて確認する

例えば、あるメンバーが静的解析を設定・実行できても、チームのCIにその検査が組み込まれていなければ、チームの品質確保には不足が残ります。一方、CIが整っていても、各メンバーがその設定を理解し、改善できるとは限りません。

評価では、次の問いを分けて確認します。

- **個人について：** 本人は、どの条件の下で、何を説明・実装・検証・改善できますか。
- **チームについて：** その取り組みは、どのリポジトリ・環境・期間で、誰が継続して運用していますか。

CIの管理権限、署名鍵やストアアカウントへのアクセス、検証用端末、担当機会などがない場合は、その制約を記録します。制約だけを理由に個人のLvを下げず、演習や過去の成果物で確認するか、未評価とします。

また、34スキルはモバイルアプリ開発領域の評価項目です。[チームチェックリスト](../checklists/index.md)に含まれるバックエンド、事業部門との連携などは、関係する専門担当者と共同で確認します。これらの能力全体を34スキルだけで評価するものではありません。
