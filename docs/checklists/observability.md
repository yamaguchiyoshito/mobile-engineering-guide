# モニタリングとクラッシュ分析

**項目No.：073〜076**

回答例は望ましい状態を示す架空の文面です。[判定方法](../guide/team-assessment.md)と[記録書式](../templates/team-assessment.md)を使い、実態と根拠を記録してください。

## C073

**チェック項目 No.073**

SLI/SLOに関わるシステムの稼働を24時間365日モニタリングしている。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

アプリが依存する API とプッシュ通知の送信基盤について SLI を定義し、可用性、応答時間、エラー率を24時間365日、自動で監視しています。アプリ側でもクラッシュが発生しなかった利用者の割合と主要操作の成功率を SLI に含め、アプリと OS のバージョン別に確認しています。SLO の評価期間・目標値・対象範囲を明記し、目標からの逸脱や急激な悪化に加えて監視の停止も検知できます。

[原文の参照先](https://dxcriteria.cto-a.org/197aa2a71774476a80eaeef043dadb1b)

## C074

**チェック項目 No.074**

エラーログを収集し、定期的（月ごと〜半年ごと）にエラーの傾向を分析し、その結果をもとに改善活動を計画している。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

Firebase Crashlytics などでクラッシュ、ANR、捕捉したエラーを収集し、サーバーのエラーログと併せて月次で傾向を分析しています。発生件数、影響する利用者数、アプリと OS のバージョン、端末、リリースとの関係を確認し、影響と頻度から改善対象を選んで担当者・期限・完了条件を設定しています。原因箇所を特定できるよう、ビルドごとにシンボル情報（dSYM、R8 のマッピングファイル）をアップロードしています。対策を含むバージョンが普及した後に発生傾向を比較し、再発の有無を確認しています。

[原文の参照先](https://dxcriteria.cto-a.org/a96a63a4179c4a319c39301411d1274c)

## C075

**チェック項目 No.075**

各種事象を調査する際にバックエンド、インフラ、フロントエンドに渡って統合されたログをトレースできるようになっている。

**望ましい原文への回答：TRUE**

原文にある取り組みを実施している状態を目指します。

### 望ましい回答例

アプリの画面操作から API、バックエンド処理、インフラの記録まで、アプリが付与するリクエスト ID やトレース ID で関連付けて調査できます。アプリのログにはアプリのバージョン、OS バージョン、端末の機種、通信状態を含め、時刻の形式をサーバー側と統一しています。個人情報や認証情報は送信前に除外し、代表的な障害を使って追跡できることを確認しています。

[原文の参照先](https://dxcriteria.cto-a.org/9dd3fd228f6240d184ef6679c88a2b88)

## C076

**チェック項目 No.076**

モニタリングにおける異常検知時のアラートが設定されていなかったり、対応フローが確立しておらず問題が解決されなかったりしている。

**望ましい原文への回答：FALSE**

原文にある問題が発生していない状態を目指します。

### 望ましい回答例

クラッシュ率の急増、特定バージョンでの新しいクラッシュ、API のエラー率、プッシュ通知の送信失敗について、検知条件、重大度、通知先、一次対応、エスカレーション、復旧確認までの手順を定めています。通知に応答がない場合の連絡経路も用意しています。定期的な訓練で通知から段階的公開の停止判断までを確認し、担当不明や通知未設定によって問題が放置される状態を防いでいます。

[原文の参照先](https://dxcriteria.cto-a.org/4e236d711c09478392092ad957948336)
